# Agentic task generation

Turn a natural-language manipulation instruction into a validated REALM task config, with a model
proposing semantics and code disposing all geometry.

The design rule is load-bearing, not stylistic: **a model may name an object, choose between
candidate assets, assert a spatial relation, and read a rendered image. It may never emit a
coordinate, an extent, a quaternion, a scale factor, or a random draw.** REALM's governing rule is
that a change which moves a number is a bug, so a family that cannot be regenerated byte-identically
under a seed is not a benchmark. Every number in an emitted config comes from the same solver the
batch generator uses.

## Quick start

Everything up to the render step runs on a laptop. The agent grounds against a small committed
asset catalogue (`../asset_catalog.json`), not the 1k-asset dataset tree.

```sh
# 0. Once, on a machine that HAS the dataset (lab workstation; no GPU needed):
python -m tooling.task_authoring.agent.catalog build \
    --dataset "$REALM_DATA_PATH/datasets/behavior-1k-assets"      # then commit asset_catalog.json
#    Until then the committed file is a ~35-category SEED taken from REALM's own task configs.
python -m tooling.task_authoring.agent.catalog show

# 1. Offline smoke test: a scripted regex agent drives the six tools. Proves the plumbing, NOT a
#    generator -- its grounding is keyword matching and it mislabels compound instructions.
uv run python -m tooling.task_authoring.agent.run data/DROID100_tabletop.json --offline \
    --report tmp/droid100/offline_report.json

# 2a. The real generator, no API key: an interactive coding agent drives the same tools via the CLI.
#     Tell it: "Follow tooling/task_authoring/agent/GENERATE_TASKS.md for the next 20 instructions."
python -m tooling.task_authoring.agent.cli next data/DROID100_tabletop.json

# 2b. The real generator, unattended: the same tools through the Anthropic API.
uv add anthropic && export ANTHROPIC_API_KEY=...
uv run python -m tooling.task_authoring.agent.run data/DROID100_tabletop.json --model <model-id> \
    --report tmp/droid100/agent_report.json

# 3. Container only: build each config, settle it, render and probe it.
./scripts/run_apptainer.sh python -u tooling/task_authoring/render_review.py \
    --family REALM_DROID100 --out tmp/droid100/review
```

A wrong `--dataset` is now an error (it used to index zero assets and decline every instruction).
The run cache is keyed on `(task_id, PROMPT_VERSION, model, catalogue fingerprint)`, so declines made
against a smaller catalogue are not replayed after the catalogue grows. Both drivers collapse
instructions that solve to the same task (`run.signature`); `--keep-duplicates` turns that off.

Step 3 is the only stage that needs a GPU, and the only one that needs the container. Inside the
container there is no `uv` -- call `python -u`. Run it on three configs first and confirm you get a
real PASS/FAIL split before submitting a sweep over the whole family.

`instructions.json` is `{"ranking_id": "...", "tasks": [{"instruction": "...", "rank": 1}, ...]}`,
or a plain text file with one instruction per line.

## The stages

| Stage | Owner | What happens |
|---|---|---|
| S1 intent | model | instruction -> task type and role nouns |
| S2 assets | model picks, code supplies | a model id that must exist in the indexed catalogue |
| S3 layout | **code** | `layout.py` calls the solver: positions, orientations, uniform scales |
| S4 validate | code | `validation.py`; errors block the write |
| S5 render | code (GPU) | `render_review.py` builds, settles, probes, renders |
| S6 review | model | findings restricted to the closed code set |
| S7 patch | **code** | a named transform re-solves; never a hand-written edit |
| S8 freeze | code | manifest + `task_id` + `prompt_version` |

## Files

| File | Role |
|---|---|
| `catalog.py` | asset catalogue snapshot (`build`/`show`), word-boundary category matching, phantom-noun check |
| `cli.py` | the six tools as shell commands, so an interactive coding agent can be the generator (see `GENERATE_TASKS.md`) |
| `layout.py` | role assignment -> solved document. The semantics/geometry boundary |
| `tools.py` | the six tool schemas and the per-instruction `Session` |
| `prompts.py` | `GENERATOR_SYSTEM`, `REVIEW_SYSTEM`, `PROMPT_VERSION` |
| `run.py` | the driver: offline scripted agent and the Anthropic tool-runner |
| `review.py` | S6/S7: parse findings, apply deterministic transforms, bounded at two iterations |
| `corrections.py` | content-keyed correction store, replacing the rank-keyed `REVIEWED_*` tables |
| `../render_review.py` | S5 harness. One config per process; `--family` fans out to children |
| `test_agent.py`, `test_catalog_cli.py` | host-safe tests; build their own synthetic asset tree |

`review.py` (S6/S7) is a library with no CLI yet: `build_review_request`, `parse_findings` and
`apply_correction` are callable and tested, but nothing reads `render_review.py`'s JSON and drives the
model in a loop from the shell. That wiring is the remaining step between S5 and S7.

## What the model cannot do

There is no `set_position`, no `set_scale`, and no `write_yaml` on the tool surface, and
`test_agent.py` asserts those names never appear. This is the mechanism, not a convention: a model
cannot take over the solver's job because no tool accepts a coordinate.

The other half is the give-up path. `report_ungroundable` exists because without an explicit way to
decline, a model substitutes a plausible-sounding asset rather than admit one does not exist. That
is how "orange-handled tool" became a mismatch a human had to catch and hard-code. A decline is a
correct answer and is recorded with its blocking terms.

## Determinism

- One RNG per concern, seeded from `--seed` (`scene_rng`, `camera_rng`, `distractor_rng`). Adding a
  fourth consumer means adding a fourth stream, never reusing one.
- Agent outputs are cached on `(task_id, prompt_version, model_id)`. A re-run with an unchanged
  cache makes no API calls and reproduces byte-identical YAML.
- `task_id = sha1(instruction + "|" + ranking_id)[:12]`, so a re-ranking keeps its review.
- Bump `PROMPT_VERSION` by hand whenever a prompt or a tool description changes. A family
  regenerated under a different prompt version is a different family.

## Verification

Host, no GPU, must stay green:

```sh
uv run ruff check realm examples tests scripts tooling
uv run python -m pytest -q tooling/task_authoring/test_validation.py \
    tooling/task_authoring/test_authoring.py tooling/task_authoring/agent/test_agent.py \
    tooling/task_authoring/agent/test_catalog_cli.py
uv run python -m tooling.task_authoring.validation \
    realm/config/tasks/REALM_DROID10 --profile authored
```

Container, against a running allocation:

```sh
./scripts/run_apptainer.sh python -u tooling/task_authoring/render_review.py \
    --task_cfg_path REALM_DROID100/<task>/default.yaml
./scripts/run_apptainer.sh python -u tests/test_scene_object_placement.py \
    --task_cfg_path REALM_DROID100/<task>/default.yaml
```

**Exit codes from the container are not trusted.** Isaac exits 0 on unhandled exceptions and
segfaults at teardown on passing runs, so `render_review.py` prints a verdict and writes it into
its JSON. Read the JSON.

Do not run `pytest tests/`: collection boots Isaac.

## Known limits

- Validation is a proxy, not a proof. Outer bboxes cannot see mesh interiors, so settling, contact
  and reachability still need the S5 harness. Do not skip it because the arithmetic passed.
- `target_state` is documentation. REALM scores from `task_progressions.yaml` keyed by `task_type`,
  so a generated task selects an existing rubric and cannot invent a success condition.
- Mass is not authorable. An unknown per-object key is swallowed by `**kwargs`, so `validation.py`
  rejects it. Making mass authorable is a `VERSION`-gated change, not generation work.
- 100 tasks x 16 perturbations is roughly 10x the current sweep. Decide whether the family runs the
  full perturbation matrix or a subset before committing cluster time.
